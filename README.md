# ФинПарус

**ФинПарус** — веб-приложение для публикации, управления и синхронизации финансовых предложений. Проект объединяет публичную витрину продуктов, внутреннюю административную панель и интеграцию с партнёрской платформой Leads.su.

Основная задача проекта — автоматизировать получение предложений от внешнего источника, хранение и обработку данных, а также их публикацию на сайте.

## Архитектура проекта

Проект построен на Django и разделяет основные обязанности между несколькими компонентами.

### Django-приложение

Отвечает за:

- обработку HTTP-запросов;
- маршрутизацию;
- работу с моделями;
- бизнес-логику;
- отображение публичной витрины;
- работу внутренних разделов;
- взаимодействие с базой данных.

### Слой интеграции

Взаимодействие с внешними системами вынесено в отдельный интеграционный модуль.

Это позволяет отделить особенности API партнёра от внутренней бизнес-логики приложения.

### Management commands

Django management commands используются для выполнения задач, которые не требуют пользовательского HTTP-запроса.

В проекте этот механизм применяется для:

- синхронизации предложений;
- запуска планировщика синхронизации;
- выполнения служебных операций.

### Фоновые процессы

Для периодического обновления предложений предусмотрен отдельный процесс синхронизации.

В production он запускается независимо от основного веб-приложения.

### Инфраструктурный слой

Docker Compose объединяет необходимые компоненты приложения:

- Django/Gunicorn;
- PostgreSQL;
- процесс синхронизации;
- Nginx для статических файлов.

## Модель данных

Основная бизнес-сущность проекта — финансовое предложение.

Модель предложения используется для хранения информации о продукте, его характеристиках, источнике данных и параметрах отображения.

### Основные понятия

**Источник (`source`)**

Идентификатор внешнего источника, из которого получено предложение.

**Внешний идентификатор (`external_id`)**

Идентификатор предложения в системе партнёра.

Совместное использование `source` и `external_id` позволяет однозначно сопоставлять внешние предложения с записями внутри приложения.

**Категория**

Позволяет объединять предложения по типу финансового продукта.

**EPC**

Показатель эффективности предложения, используемый при оценке и сортировке продуктов.

**Порядок сортировки (`sort_order`)**

Определяет порядок отображения предложений.

**Активность**

Позволяет управлять доступностью предложения на публичной витрине.

### Важные принципы работы с моделью

- Внешнее предложение должно иметь возможность однозначного сопоставления с внутренней записью.
- Повторная синхронизация не должна создавать дубликаты.
- Обновление данных не должно приводить к потере внутренних настроек без необходимости.
- Неактуальные предложения не должны продолжать отображаться как действующие.
- Изменения структуры модели должны сопровождаться миграциями Django.

## Интеграция с Leads.su

Интеграция с Leads.su предназначена для автоматического получения финансовых предложений из партнёрской системы.

Основная реализация находится в:

```text
project/showcase/integrations/leads_su.py
```

Интеграционный слой отвечает за взаимодействие с внешним API и получение данных, необходимых для последующей обработки приложением.

### Общий процесс интеграции

```text
Leads.su API
     |
     v
Получение внешних данных
     |
     v
Обработка ответа API
     |
     v
Преобразование данных
     |
     v
Сопоставление с существующими предложениями
     |
     v
Создание или обновление записей
     |
     v
Актуализация статусов предложений
     |
     v
Публичная витрина
```

### Принципы интеграции

1. Внешние данные поступают из API Leads.su.
2. Полученные данные обрабатываются интеграционным модулем.
3. Данные приводятся к внутренней структуре приложения.
4. Для поиска существующих записей используется идентификация по источнику и внешнему идентификатору.
5. Новые предложения создаются в базе данных.
6. Существующие предложения обновляются.
7. Предложения, которые перестали поступать от источника, обрабатываются согласно логике синхронизации.

### Обработка ошибок

При работе с внешним API необходимо учитывать:

- недоступность API;
- ошибки HTTP;
- некорректные ответы;
- изменение структуры внешних данных;
- отсутствие отдельных полей;
- проблемы сетевого соединения;
- ошибки записи данных в базу.

Ошибки интеграции не должны приводить к неконтролируемому повреждению внутренних данных.

## Синхронизация предложений

Для запуска синхронизации используется Django management command:

```bash
python manage.py sync_leads_offers
```

Команда выполняет получение и обработку предложений из Leads.su.

### Основные этапы синхронизации

#### 1. Получение данных

Команда обращается к интеграционному модулю и получает данные из внешнего источника.

#### 2. Идентификация предложений

Для сопоставления используется комбинация:

- `source`;
- `external_id`.

Это позволяет отличать предложения разных источников и предотвращать появление дубликатов.

#### 3. Создание новых записей

Если соответствующее предложение отсутствует в базе данных, создаётся новая запись.

#### 4. Обновление существующих записей

Если предложение уже существует, его данные актуализируются на основании информации из внешнего источника.

#### 5. Обработка отсутствующих предложений

Предложения, которые больше не поступают от источника, могут деактивироваться.

Это позволяет не показывать пользователям предложения, которые больше не являются актуальными.

### Транзакционность

При выполнении операций синхронизации важно сохранять целостность данных.

Изменения должны выполняться с учётом транзакционной логики, чтобы ошибки обработки не приводили к частично обновлённому состоянию базы данных.

### Режим предварительной проверки

Для безопасной проверки синхронизации предусмотрен режим `dry-run`.

Он предназначен для предварительного анализа предполагаемых изменений без фактического применения обновлений к базе данных.

Точный синтаксис параметров команды следует смотреть в её реализации.

## Автоматический запуск синхронизации

Для периодического запуска обновления предложений предусмотрен отдельный планировщик.

Файл команды:

```text
project/showcase/management/commands/run_offer_sync_scheduler.py
```

Планировщик позволяет выполнять синхронизацию без ручного запуска management command.

### Интервал синхронизации

Периодичность задаётся переменной окружения:

```env
SHOWCASE_SYNC_INTERVAL_SECONDS=3600
```

Значение указывается в секундах.

Например:

| Значение | Интервал |
|---:|---|
| `300` | 5 минут |
| `900` | 15 минут |
| `1800` | 30 минут |
| `3600` | 1 час |
| `21600` | 6 часов |
| `86400` | 24 часа |

Фактический интервал определяется значением переменной окружения и логикой планировщика.

### Рекомендации

- Не запускать несколько независимых планировщиков без необходимости.
- Контролировать логи фонового процесса.
- Учитывать ограничения API партнёра.
- Не допускать параллельного выполнения конфликтующих операций синхронизации.
- Проверять состояние базы данных после изменения логики импорта.

## Локальная разработка

### Требования

Для запуска проекта локально необходимы:

- Python;
- PostgreSQL;
- Git;
- pip.

Docker может использоваться для запуска инфраструктурных компонентов.

### 1. Клонирование репозитория

```bash
git clone https://github.com/ivanlbdv/showcase.git
cd showcase
```

### 2. Создание виртуального окружения

```bash
python -m venv .venv
```

Активация в Linux/macOS:

```bash
source .venv/bin/activate
```

Активация в Windows:

```powershell
.venv\Scripts\activate
```

### 3. Установка зависимостей

```bash
pip install -r requirements.txt
```

### 4. Настройка окружения

Создайте файл `.env` в соответствии с настройками проекта.

Пример конфигурации:

```env
SECRET_KEY=your-secret-key
DEBUG=True

DATABASE_URL=postgresql://user:password@localhost:5432/showcase

LEADS_SU_API_KEY=your-api-key

SHOWCASE_SYNC_INTERVAL_SECONDS=3600
```

Названия и обязательность переменных необходимо сверять с `settings.py` и кодом интеграции.

### 5. Применение миграций

Перейдите в каталог Django-проекта:

```bash
cd project
```

Выполните миграции:

```bash
python manage.py migrate
```

### 6. Создание суперпользователя

```bash
python manage.py createsuperuser
```

### 7. Запуск сервера разработки

```bash
python manage.py runserver
```

Приложение будет доступно по адресу:

```text
http://127.0.0.1:8000/
```

## Переменные окружения

Конфигурация приложения должна задаваться через переменные окружения, а не через значения, зафиксированные в исходном коде.

Пример основных параметров:

| Переменная | Назначение |
|---|---|
| `SECRET_KEY` | Секретный ключ Django |
| `DEBUG` | Режим отладки |
| `DATABASE_URL` | Строка подключения к базе данных, если используется соответствующая конфигурация |
| `LEADS_SU_API_KEY` | Ключ доступа к API Leads.su |
| `SHOWCASE_SYNC_INTERVAL_SECONDS` | Интервал автоматической синхронизации в секундах |

Полный перечень переменных определяется фактической реализацией настроек Django, интеграции и Docker Compose.

### Правила хранения секретов

- Не добавлять `.env` в Git.
- Не хранить API-ключи непосредственно в исходном коде.
- Не публиковать `SECRET_KEY`.
- Использовать GitHub Secrets для секретов CI/CD.
- Использовать отдельные значения для локального и production-окружения.

### Production-сервисы

В конфигурации предусмотрены следующие компоненты:

| Сервис | Назначение |
|---|---|
| `web` | Основное Django-приложение под Gunicorn |

### Назначение компонентов

**web**

Обрабатывает пользовательские HTTP-запросы и запускает Django через Gunicorn.

**sync**

Выполняет периодическую синхронизацию предложений из внешнего источника.

**db**

Хранит данные приложения в PostgreSQL.

**nginx-static**

Обеспечивает обслуживание статических файлов и соответствующую веб-инфраструктуру.

### Важные особенности production

- Секретные параметры должны передаваться через окружение.
- База данных должна сохранять данные между перезапусками контейнеров.
- Фоновая синхронизация должна работать независимо от веб-процесса.
- После обновления приложения необходимо учитывать миграции базы данных.
- При изменении статических файлов необходимо повторно выполнять их сборку.
- Состояние сервисов следует контролировать через Docker Compose и логи.

---

## Статические файлы

Для подготовки статических файлов Django используется команда:

```bash
python manage.py collectstatic --noinput
```

Сборка статических файлов необходима после изменений CSS, JavaScript, изображений и других ресурсов, которые обслуживаются как static files.

В production их обслуживание вынесено в инфраструктурный слой с использованием Nginx.

## CI/CD

В репозитории используются GitHub Actions.

Workflow находятся в каталоге:

```text
.github/workflows/
```

### CI

Файл:

```text
.github/workflows/ci.yml
```

Предназначен для автоматизации проверок проекта.

CI позволяет обнаруживать ошибки до развёртывания приложения.

### Deploy

Файл:

```text
.github/workflows/deploy.yml
```

Предназначен для автоматизации production-развёртывания.

В инфраструктуре используется GitHub Container Registry (GHCR) для хранения Docker-образов.

### Общий процесс доставки изменений

```text
Изменение исходного кода
          |
          v
     Git push
          |
          v
   GitHub Actions
          |
          v
  Автоматические проверки
          |
          v
 Сборка Docker-образа
          |
          v
 Публикация образа в GHCR
          |
          v
 Production-развёртывание
```

Конкретные условия запуска workflow, используемые теги образов и список секретов определяются файлами CI/CD.

### Секреты GitHub

Для работы автоматизированного развёртывания используются GitHub Secrets и переменные окружения.

Секреты должны соответствовать требованиям deployment workflow.

## Режим обслуживания

При эксплуатации приложения необходимо учитывать возможность временного ограничения доступа к публичной части.

Режим обслуживания используется для ситуаций, когда требуется:

- обновить приложение;
- выполнить технические работы;
- проверить инфраструктуру;
- провести обслуживание базы данных;
- устранить критическую ошибку.

При включении такого режима важно сохранить доступ к необходимым административным и техническим операциям в соответствии с настройками приложения.

## Безопасность

### Django

- Использовать надёжный `SECRET_KEY`.
- Не включать `DEBUG=True` в production.
- Ограничивать список разрешённых доменов.
- Проверять права доступа к административным представлениям.
- Не публиковать конфиденциальные настройки.

### API-интеграция

- Хранить ключи API в переменных окружения.
- Обрабатывать ошибки внешних запросов.
- Проверять структуру получаемых данных.
- Учитывать ограничения внешнего API.
- Не допускать некорректного обновления внутренних данных.

### Инфраструктура

- Не хранить пароли и токены в Git.
- Использовать защищённые настройки production.
- Контролировать доступ к серверу.
- Следить за актуальностью зависимостей.
- Обеспечивать резервное копирование базы данных.

## Рекомендации по разработке

3. Проверить миграции локально.

1. Проверить представления.

3. Проверить фильтрацию и сортировку.
4. Проверить отображение неактивных предложений.
5. Проверить адаптивность интерфейса.

- Запустить тесты.
- Проверить миграции.
- Проверить настройки окружения.
- Убедиться в отсутствии секретов в коммитах.
- Проверить сборку Docker-образа.
- Убедиться в корректности конфигурации Docker Compose.

## Архитектурные принципы

При дальнейшем развитии проекта рекомендуется сохранять следующие принципы:

1. **Разделение ответственности.** Интеграция с внешними системами должна быть отделена от пользовательских представлений.
2. **Повторяемость операций.** Повторная синхронизация не должна создавать дублирующие записи.
3. **Целостность данных.** Обновление предложений должно учитывать транзакционность и согласованность базы данных.
4. **Безопасность.** Секреты и параметры окружения не должны находиться в исходном коде.
5. **Изолированность процессов.** Веб-приложение и фоновая синхронизация должны иметь независимые процессы запуска.
6. **Воспроизводимость.** Локальное и production-окружения должны быть воспроизводимы с помощью конфигурации проекта.
7. **Поддерживаемость.** Новая функциональность должна соответствовать существующей структуре приложения.
